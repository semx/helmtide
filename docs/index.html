helmtide

Helm-native release management for a whole set of releases, from one file.
A maintained fork of helmwave, running on Helm 4.

GitHub Install Issues Attribution

What this is

helmwave deploys a whole set of Helm releases from one file: a planfile you can review before applying, a dependency graph instead of a wall of helm upgrade calls, live resource tracking through kubedog, and helm linked in as a library rather than shelled out to. The design is good.

It stopped receiving releases in December 2025, with its own release pull request left open and contributions unreviewed since. helmtide picks it up from there.

This is a fork, not a replacement. The design and almost all of the code belong to Dmitriy Zhilyaev and the helmwave contributors, under MIT. helmtide is not endorsed by or affiliated with them — please do not send them helmtide bugs. If upstream maintenance resumes, the changes here are offered back.

What is different

It runs on Helm 4

Upstream is on Helm 3, whose support ends in November 2026; asking for Helm 4 is what people have been doing in its issues. helmtide builds on helm.sh/helm/v4. Charts written for Helm 3 keep working — Chart API v2 is unchanged in Helm 4.

No known vulnerabilities

govulncheck reported 33 that the code actually reaches — among them helm 3.18.4 (panic on malformed YAML, memory exhaustion through a crafted JSON schema), go-getter 1.7.8 (symlink attacks, reached from downloadRemoteSrc) and go-git 5.13.0 (credentials forwarded across a redirect to another host).

Updating dependencies took that to 4; moving to Helm 4 took it to 0, because containerd and x/crypto/openpgp left the module graph with Helm 3's OCI client. CI fails on a new one.

The test suite cannot reach your cluster

Running the suite used to send helm dry-runs at whatever ~/.kube/config pointed to. On the machine this fork was started on that was a production EKS endpoint, and it only failed because the credentials had expired.

Importing the test helpers now pins KUBECONFIG to a kubeconfig that goes nowhere, and the tests that genuinely need an API server skip with a reason instead of failing with cluster unreachable. go test ./... is green on a laptop with no cluster and no credentials.

Community fixes that were waiting upstream

Reviewed, ported and credited to their authors — a duplicate pre_build hook invocation, and offline_kube_version still requiring a live cluster.

Migrating from helmwave

An existing setup runs as it is, with one exception — recreate: is gone, because Helm 4 has nothing behind it.

you havehelmtide
helmwave.ymlused as-is when there is no helmtide.yml
helmwave.yml.tplsame
HELMWAVE_* variablesstill read; HELMTIDE_* wins when both are set
recreate:removed — Helm 4 has no field behind it
wait: true / falsestill accepted; also takes watcher, legacy, hookOnly

So helmtide build works in a repository written for helmwave, and you can migrate one file at a time.

Install

go install github.com/semx/helmtide/cmd/helmtide@latest

Usage

helmtide build      # render the plan
helmtide up         # apply it

The helmwave documentation still describes the configuration format accurately. Where helmtide diverges it is written down in the README.

Reporting a vulnerability

Send it to securityreport@sannikov.dev or @sannikovdev rather than opening a public issue. Bugs in helmwave itself belong to their policy, not to this address.
